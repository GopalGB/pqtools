# pqtools 0.5.0 - "pandas for Power Query" builtin expansion

## Goal (the terminal condition)

A Power Query query **generated by Power Query's own UI** - not a hand-crafted test case - runs
end-to-end under `pq eval` once its connector step is supplied via `--bind`. Today it fails on
step 2 of literally every GUI query, because `Table.TransformColumnTypes` is not implemented.

**Done means:** the four real-world reference queries in `tests/fixtures/realworld/` evaluate to
correct results, and `pq eval` on each produces the expected CSV. Not "N functions added".

## Non-goals (do not attempt, these are the permanent wall)

Connectors (`File.Contents`, `Web.Contents`, `Sql.Database`, `Excel.Workbook`, `SharePoint.*`,
`OData.Feed`, ...), credentials, query folding, DAX, data refresh. These require Microsoft's
Mashup Engine. They must keep raising `UnsupportedError` naming the construct. **Never approximate
a connector's result.** An unimplemented construct raises; it never guesses.

## Architecture change (do this first, it is the foundation)

`src/pqtools/evaluate.py` is 1310 lines and will roughly triple. Split the builtins into a package
BEFORE adding to it, with **zero behaviour change**:

```
src/pqtools/builtins/__init__.py   # BUILTINS registry, assembled from the modules
src/pqtools/builtins/_shared.py    # _arity, _require_table, _require_number, _require_text, errors
src/pqtools/builtins/_table.py     _text.py  _list.py  _record.py
src/pqtools/builtins/_number.py    _datetime.py  _type.py  _splitter.py
```

`evaluate.py` keeps the evaluator core (scopes, `let`, `each`, invocation, `try`) and imports the
registry. Existing helper signatures `(args: list[Any], ctx: _Ctx) -> Any` stay exactly as they are.
**All 197 existing tests must pass unchanged after the refactor** - it is a pure move.

## Correctness rules (non-negotiable)

1. **Match real Power Query semantics, not intuition.** Where you are unsure of an edge case,
   implement the documented behaviour and add a test that pins it. Where you cannot determine it,
   raise `UnsupportedError` rather than guess. A wrong silent answer is worse than a refusal.
2. `null` propagation: most `Table.*`/`Text.*` functions return `null` on `null` input rather than
   throwing. Follow the documented per-function behaviour.
3. Sorting is stable; `Table.Sort` already handles the `{{"col", Order.Ascending}}` shapes the UI
   emits - do not regress it.
4. Errors: keep the `EvalError` / `UnsupportedError` split. `UnsupportedError` = "pqtools cannot do
   this"; `EvalError` = "your query is wrong" (bad column, type mismatch, arity).
5. Every function added gets at least one test; every function whose semantics you had to reason
   about gets an edge-case test too.
6. `_arity` on every builtin. No unbounded loops over caller-supplied counts without a step budget
   (the evaluator has `max_steps` - respect it).

## Findings from the fixture round (read these before implementing)

1. **Optional record-option arguments are mandatory, not decoration.** Real PQ emits
   `Table.PromoteHeaders(Source, [PromoteAllScalars=true])` and
   `Table.SplitColumn(..., Splitter.SplitTextByDelimiter(",", QuoteStyle.Csv), ...)`. Any function
   that takes an options record must accept it and honour the options it documents - silently
   ignoring an options record is a wrong answer, not a simplification. Where an option is not
   implemented, raise `UnsupportedError` naming the option.
2. **The evaluator resolves a call's callee identifier before evaluating its arguments**, so a
   query fails on the LAST unimplemented builtin reachable walking back from `in`, not the first
   one written. Consequence: implementing one function in a chain just moves the wall to the next.
   **Land whole families together**, and treat a fixture as proof only when its entire chain runs.
   Do not celebrate an error message changing - that is not progress toward the goal.
3. Fixture CSVs deliberately carry `Column1,Column2,...` headers with the real headers as the first
   data row, because that is what `Csv.Document` actually returns - so `Table.PromoteHeaders` has
   genuine work to do. Do not "fix" the fixtures to have real headers.

## Integration backlog (found during the parallel round - owner: integration pass)

1. **`table[Column]` (table-column access) is not implemented in the evaluator core.** `evaluate.py`'s
   field access only handles a record (single row); real M also allows `[Col]` on a TABLE, yielding the
   list of that column's values. This is why `each List.Sum([Amount])` - the single most common
   `Table.Group` aggregation the UI writes - fails with `cannot select a field from a list value`.
   Fix in `evaluate.py`: when the base is a `list[dict]`, return `[row.get(name) for row in base]`.
   Pinned by an xfail in `tests/test_builtins_join.py::test_group_direct_column_shorthand_in_aggregation`
   which flips green on fix. **This is not optional - scenario 02 cannot pass without it.**
2. `Table.NestedJoin` refuses `RightOuter`/`RightAnti`/`FullOuter` because the implementer could not
   verify which side becomes the nested column for the direction-flipped kinds. Resolve from Microsoft's
   published docs and implement, or leave the refusal and document it in README Limits. Do not guess.
3. Reported but deliberately unfixed during the refactor (pre-existing, all in `_table.py`): the
   "column exists" checks in `Table.AddColumn` / `Table.RenameColumns` / `Table.Sort` inspect only the
   FIRST row's keys, so heterogeneous rows can silently overwrite a column or raise a bare `KeyError`
   instead of `EvalError`.
4. **`Table.AddColumn` takes an optional 4th argument (the column type)** and `_table.py`'s
   implementation only accepts 3, so the UI's `Table.AddColumn(t, "Year", each Date.Year([D]), Int64.Type)`
   raises `UnsupportedError: Table.AddColumn with 4 argument(s)`. **Blocks scenario 04.** `_table.py` was
   not assigned to any parallel agent, so this is the integration pass's job.
5. Two tests in `tests/test_evaluate.py` now fail because they *encoded current limitations as expected
   behaviour* - the same anti-pattern as the old `Table.Sort` "unsupported Order enum" test:
   - `test_type_value_is_unsupported` - `type text` is now supported, so this must assert the new
     behaviour rather than the old refusal.
   - `test_unknown_builtin_style_identifier_is_unsupported` - used `Table.AddIndexColumn` as its example
     of an unimplemented name; that is now implemented. Swap in a name that will stay unimplemented
     (prefer a connector, which is permanently out of scope by design, e.g. `Sql.Database`).
   Neither is a regression. Both must be rewritten, not deleted, and not "fixed" by removing coverage.
